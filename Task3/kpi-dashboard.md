# Панель KPI эксплуатации целевой архитектуры

**ТЗ** означает обязательную цель задания. **SLO-предложение** - параметр для согласования G0/G2; он ещё не является измеренным результатом. Метрики ошибок, времени и полноты считаются раздельно. Удаление неуспешных или медленных событий из знаменателя запрещено.

| Технический показатель (KPI) | Целевое значение метрики | Способ и инструмент замера (инструментарий/формула) | Бизнес-смысл - какую проблему решает замер |
| --- | --- | --- | --- |
| K01. Доступность транзакционного ядра по времени | **ТЗ:** >=99.95% 24/7 за календарный год; месячный rolling SLO той же величины - предложение. | 100 * (T - T_bad) / T. Синтетические сценарии создания заказа/принятия отгрузки из независимых зон каждые 10 с, Prometheus Blackbox + traces и журнал инцидентов. Отказ операции, timeout или недопустимое время ответа означают bad-интервал; плановый простой включён. Уточнение границ интервалов по журналу, не только по частоте проб. | Ограничивает время недоступности продаж/отгрузок, включая периоды без пользовательского трафика. |
| K02. Успешность валидных запросов ядра | **SLO-предложение:** >=99.95% за 30 дней; отдельно от K01. | Good valid requests / all valid requests. Gateway + Orders/Delivery: 5xx, timeout, перегрузочный 429 и нарушение согласованного latency SLO - bad; пользовательские 4xx учтены отдельно. 202 считается лишь принятием, завершение отслеживает K07. | Не позволяет скрыть клиентские отказы за формальным uptime или объявить 202 подтверждённой отгрузкой. |
| K03. Суточная производительность | **ТЗ:** 500 000 отправлений/сутки. | count уникальных подтверждённых бизнес-отправлений по shipment_id за сутки UTC+3 в авторитетном домене; сверка с принятыми заказами/очередью. 24-часовой soak-тест со сценарием полного жизненного цикла. | Подтверждает способность обслуживать десятикратный объём, а не считать retries новыми отправлениями. |
| K04. Пик создания заказов | **ТЗ:** 200 RPS; **SLO-предложение:** p99 durable ACCEPTED <=500 мс, доля технических отказов <=0.05% на часовом пике. | Gateway rate валидных create + Orders created_total/idempotency; OTel histogram до commit/ответа. Совместный тест с K05, наблюдать каждый миллион/окно выборки и квоты БД. | Заказы продолжают приниматься при высокой телематической нагрузке; подтверждение наличия товара - отдельная стадия. |
| K05. Приём телеметрии | **ТЗ:** 3000 RPS записи; **SLO-предложение:** p99 durable ACK <=200 мс. | Уникальные device_id+sequence, ingress rate, Kafka ACK/ISR и журнал устройства; сравнение множества подтверждённых ID с восстановленным журналом. Неподтверждённые события повторяются устройством. | Координаты не теряются при отказе склада/биллинга; ACK выдаётся только после надёжной записи. |
| K06. Свежесть ключевых статусов в DWH | **ТЗ:** каждое валидное изменение отражено <=5 с; цель действует уже в M3. | L = DWH commit_time - source commit_time; change_id/commit LSN во внутреннем audit ledger связывает событие с обновлением агрегата. Внешнему DWH внутренний ID не раскрывается. OTel + receipt DWH + canary; p50/p95/p99, max и число L>5 с. Погрешность часов измеряется; вывод <=5 с делается с её учётом. | Руководство видит актуальные операции; время до Kafka или p99 не подменяют требование полного сквозного пути. |
| K07. Согласованность EDI | **ТЗ:** 0 недопустимых переходов/повторных эффектов; **SLO-предложение:** p99 применения готового документа <=5 с после выполнения его предусловий. | Корреляция sender+document+revision, inbox/outbox, версии Saga и сверка allocation/invoice. Проверки ORDERS -> DESADV -> INVOIC; отдельно возраст parking и DLQ. Время физической отгрузки не входит в технические 5 с. | Нет оплаты необеспеченного счёта, повторных накладных и ложного завершения логистического процесса. |
| K08. Полнота учёта платежей | **ТЗ:** 0% навсегда потерянных результатов из-за timeout; **SLO-предложение:** все доступные терминальные статусы банка сопоставлены после окна сверки <=5 минут. | Unmatched terminal provider transactions / total terminal provider transactions =0 по реестру банка и merchant_payment_id. Durable inbox, status API и reconciliation; отчёт по каждой неизвестной операции. Если банк/реестр недоступен, полнота помечается неизвестной, а не 100%. | Тайм-аут не превращается в потерю денег или повторное списание. |
| K09. Возраст UNKNOWN и дубли платежа | **SLO-предложение:** 0 двойных финансовых эффектов; UNKNOWN старше 5 минут - инцидент, не автоматическое повторное списание. | Уникальность merchant_payment_id/provider operation + outbox/inbox; gauge oldest_unknown_seconds, reconciliation diff, sandbox с потерянным ответом/повтором. | Сохраняет резерв и даёт оператору управляемый разбор спорного платежа. |
| K10. Доступ CRM к истории | **SLO-предложение:** p99 API <=1 с; lag проекции <=5 с, 0 прямых SQL-соединений CRM к доменным БД. | OTel API histogram, last_applied_event_time, freshness в ответе; сетевой аудит и отказ SQL-подключения. API не ждёт синхронного JOIN нескольких доменов. | Поддержка видит историю быстро и не нагружает транзакционную БД. |
| K11. Разделение ПДн и платёжных данных | **ТЗ:** 0 паспортов/телефонов/email в операционных доменных БД/экспорте; 0 PAN/CVV в Fast Cargo по штатным контрактам. | Реестр полей/потоков, contract tests allowlist, DLP/лог-аудит, проверка browser/network пути оплаты; сканирование само не является полным доказательством. Profile/Vault и закрытые переходные копии имеют отдельный доступ/учёт. | Ограничивает утечки при подключении CRM/DWH; оплата не вводит карточные данные в инфраструктуру Fast Cargo. |
| K12. Запас журнала и consumer lag | **SLO-предложение:** capacity на 24 ч непрерывного максимума IoT при 1 KiB; warn при диске 70%, critical 80% или времени до исчерпания <30 мин. | Kafka offsets/records_lag, bytes/sec, disk_used, retention horizon; прогноз T_full=free_bytes/net_growth_bytes_per_sec. Раздельные дашборды IoT/business. | Даёт время восстановить sink до потери событий по retention и не угрожает заказам. |
| K13. Восстановление ядра | **SLO-предложение:** RTO<=15 минут, RPO=0 для подтверждённых записей при отказе одного узла/зоны; полный site disaster оценивается отдельно. | Rehearsal failover/fencing: время от отказа до прохождения критичных синтетических сценариев; сверка подтверждённых ID после восстановления. Backup/PITR проверяется восстановлением, не только наличием файла. | Проверяет способность возобновить отгрузки и защитить уже принятые команды. |
| K14. Независимость потоков | **ТЗ:** склад/биллинг не замедляют создание заказов и не теряют геоданные. **SLO-предложение:** в таком тесте соблюдены K04/K05. | Остановить Warehouse/Finance при совместном пике, сравнить Orders p99/отказы и множества подтверждённых IoT ID; отдельно наблюдать pending Saga. | Отказ одного домена становится управляемой задержкой процесса, а не общим падением. |
| K15. Результат перехода M3 | **ТЗ:** код legacy неизменен и 0 дополнительных SELECT коннектора на primary. | Checksum исходников, аудит доступов/SQL-сессий по существующим средствам, конфигурация адреса replica, отсутствие credentials к primary SQL, сверка LSN на replica. Новые проверки сами не должны добавлять SELECT на primary. | Защищает текущие отгрузки от скрытой стоимости промежуточной аналитики. |
| K16. Завершение M12 | **ТЗ:** 0 рабочих legacy writers, междоменных SQL JOIN и распределённых DB-блокировок. | Инвентаризация маршрутов/сетевых прав/схем/зависимостей и журналы обращений за месяц; полный жизненный цикл без legacy; проверка удаления временного CDC/ACL. | Подтверждает демонтаж монолита и отсутствие скрытой общей базы. |

## Бюджеты и правила измерения

- Для невисокосного года 99.95% допускает 15 768 секунд =262.8 минуты =4 ч 22 мин 48 с недоступности. Для 30 дней -21.6 минуты. В реальном SLA используется длительность конкретного периода; нельзя выдавать запросную долю за время доступности.
- Жёсткий предел DWH 5 с контролируется по всем валидным событиям и canary; позднее событие является нарушением даже при хорошем p99. Во время outage фиксируются latency violation и backlog, а не удаляется неудобное наблюдение.
- Суточные 500 000 отправлений дают среднее 5.79/с; пик 200 RPS создания не предполагается постоянным на протяжении суток. Профиль заказов, число статусов и коэффициент событий на заказ определяются тестом.
- Бизнес-термины "создан", "принят", "подтверждён", "отгружен" согласуются с логистикой. Устройство, банковский ответ и документ EDI не признаются надёжно принятыми до долговременной записи.

## Представления и действия

| Представление | Владелец | Что видно и что происходит при нарушении |
| --- | --- | --- |
| Executive | Операционный блок, генеральный директор | K01/K03/K06/K08: объём, свежесть и спорные платежи. Денежные потери считаются только после утверждения модели маржи/простоя. |
| Service/SRE | SRE, техлид, владельцы доменов | K02/K04-K10/K14: latency, ошибки, lag и business pending. Error-budget burn вызывает инцидент/остановку рискованных релизов. |
| Infrastructure | Платформа, DBA | ISR, disk/WAL, пулы, IOPS и recovery. Порог исчерпания вызывает расширение/ограничение нового потока по runbook, не рост числа writers. |
| Security/data | ИБ, владелец ПДн/DWH | K11/K15/K16: разрешённый состав, границы, аудит доступа. При утечке закрывается экспорт/раскрытие, сохраняется журнал расследования. |

Порог наличия проблемы и получатель алерта проверяются на rehearsal. SLA внешнего банка и DWH согласуются отдельно; задача не решается вычитанием их аварий из статистики ядра без договора.
